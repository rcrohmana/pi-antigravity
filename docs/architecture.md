# Architecture

Pi remains the parent process. Each role tool validates input and working-directory policy, then starts one official `agy.exe` process with `shell: false`, `--input-format stream-json`, `--output-format stream-json`, the selected role, and a parent-side timeout. The one-turn JSON user event is written to stdin and stdin is closed, avoiding Windows argv limits.

## Child environment isolation (A-04)

The runner separates the parent-resolution environment from the child environment. The source environment (`options.env` injection point, otherwise `process.env`) is used only before spawn: to resolve the executable and to copy allow-listed variables. `buildAgyChildEnv()` constructs a fresh null-prototype object on every call containing only the allow-listed names found as non-empty string data values — `PATH` on all platforms, the Windows process/profile set (`SystemRoot`, `WINDIR`, `ComSpec`, `PATHEXT`, `TEMP`, `TMP`, `USERPROFILE`, `HOMEDRIVE`, `HOMEPATH`, `LOCALAPPDATA`, `APPDATA`, `ProgramData`, `LOGONSERVER`, `SYSTEMDRIVE`, `USERDOMAIN`, `USERNAME`) on `win32`, and the POSIX set (`HOME`, `TMPDIR`, `TMP`, `TEMP`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_CACHE_HOME`, `USER`, `LOGNAME`) on `linux`/`darwin`. Missing source variables stay missing; nothing is synthesized, spread, or pass-through, and there is no task/configuration extension point. Provider keys, generic CI, proxy, custom-CA, Node preload, and Pi variables are therefore absent from the object handed to `spawn()`.

All environment reads use one shared lookup helper with deterministic semantics: own data properties only, non-empty string values only, accessors ignored without invoking their getters, exact-case matching on Linux/macOS, and on Windows a case-insensitive match resolved by JavaScript's default code-unit ordering of the raw keys with canonical output spellings. The Windows allow-list includes the identity variables `LOGONSERVER`, `SYSTEMDRIVE`, `USERDOMAIN`, and `USERNAME` because the Node/libuv runtime on Windows otherwise copies that fixed variable set from ambient `process.env` into any child whose spawn options omit it, below the extension's boundary. To close that ambient-source bypass, every `runAgy()` invocation on win32 — regardless of which spawn implementation is injected, since a wrapper could reach the real process — requires the full libuv set (`HOMEDRIVE`, `HOMEPATH`, `LOGONSERVER`, `SYSTEMDRIVE`, `SystemRoot`, `TEMP`, `USERDOMAIN`, `USERNAME`, `USERPROFILE`, `WINDIR`) to exist as non-empty source values in `options.env` and fails closed before executable resolution and spawn with diagnostics that name only the missing variables; only direct helper tests exercise partial win32 environments. Executable resolution (`AGY_CLI_PATH`, then `PATH`, then the Windows `%LOCALAPPDATA%`/`%USERPROFILE%` fallback) uses the same helper and normalizes every candidate to an absolute path before acceptance; `options.executable` must be absolute for every invocation, including injected fake spawn implementations; unsupported platforms (`win32`, `linux`, `darwin` only) fail before `exists()`, environment construction, or process creation. The source environment object and `process.env` remain unchanged across success and every tested failure/cancellation path. Runner-generated diagnostics may name canonical environment variables but never serialize their values; child-controlled stdout/stderr remains verbatim-but-bounded and is not value-screened.

The offline tests prove the exact object passed to `spawn()` and ordinary descendant inheritance: a real child/grandchild canary fixture verifies that the actual child and grandchild process keys match only the expanded allow-list, with no runtime-injection exception. `runAgy()` requires the selected platform to equal the host platform and fails closed on a mismatch before any environment or spawn work, because libuv injection and path semantics follow the actual host — a simulated platform string is not runner validation. These tests do not replace the owner-gated live synthetic-canary acceptance for the tested Agy version, and no live acceptance has been recorded yet. Linux and macOS are supported by code but unvalidated.

`cwd` validation constrains only the child process working directory; it is not a filesystem write sandbox. The effective file-operation scope is defined by the owner's Agy `read_file(...)` / `write_file(...)` permission rules. Role prompts ask agents to stay in the selected workspace, but that is a behavioral instruction rather than a hard path-control mechanism.

The runner incrementally parses only documented `init`, `step_update`, and `result` events. It forwards bounded progress to Pi, requires a terminal `SUCCESS` result, and returns response, status, usage, conversation ID, duration, and bounded diagnostics. Every model-visible final response and error is centrally limited to 50 KiB UTF-8 and 2,000 lines with an explicit truncation marker; escalation/diagnostic notices are retained when truncating. Non-zero exits, non-success statuses, malformed events, missing results, timeout, and cancellation are failures. Timeout and abort terminate the whole child tree: `taskkill /T /F` on Windows, and on Linux/macOS a signal to the child's process group (the child is spawned `detached` as a group leader, so commands Agy started are included), with a direct SIGTERM/SIGKILL fallback. Once a call has settled (including a forced rejection after the termination grace period), a late `close` or buffered stdout is ignored, so no progress update reaches Pi after the tool returned. Error messages carry their diagnostics exactly once, appended by the shared output bounding so they survive truncation.

Headless permission behavior (verified on CLI 1.1.25; details in `docs/permissions.md`): without matching allow rules, headless Agy auto-denies `read_file`/`read_url` even inside the workspace. The effective Windows rule form is `read_file(C:/Users/<you>/...)`. The plugin frontmatter `tools` allow-list is enforced at runtime — `init.tools` advertises the full CLI catalog, but tools outside a role's list are uncallable, and the model escalates explicitly instead of attempting them. Commands (`run_command`) work headlessly only with matching `command()` allow rules and WITHOUT the `--sandbox` flag — with it, every command hits `escalate_admin` auto-denial; per project-owner decision the runner does not emit `--sandbox`, so command safety relies on scoped `command()` rules, the Pi write gate, and deny rules.

The extension never reads Agy credentials or serializes the Pi conversation. Only `task`, explicitly supplied `context`, and explicitly supplied file hints are sent. The role's execution mode and agent selection are fixed by extension code rather than task text. Scout and researcher run in Agy's flagless default mode (the `--mode` flag is omitted entirely because CLI 1.1.25 only accepts `accept-edits` or `plan`); worker and delegate use `--mode accept-edits` after Pi confirmation.

`worker` and `delegate` are write-capable and require a Pi UI confirmation; they are denied when `ctx.hasUI` is false. Scout is local-only. Researcher is web-only (`search_web` and `read_url_content`) and rejects file hints, so it cannot read local files even when Agy permissions allow other roles to do so. Supplying explicit context to researcher requires a Pi UI confirmation and is denied headlessly because that context could be exposed through a broad web-fetch policy. All four plugin agents set `inheritCustomizations: false` so ambient skills, rules, MCP servers, and nested-agent customizations cannot silently expand the role contract.

## Prompt assembly

`buildAgyPrompt()` in `src/runner.ts` assembles the one-turn user message sent to Agy over stdin, in a fixed order:

1. **Workspace line:** the canonical `cwd`, JSON-quoted, followed by an instruction to use it for all local file operations and not search outside it.
2. **Task:** the caller-supplied task text, verbatim.
3. **Explicit parent context**, only when supplied, labeled "(untrusted)" so the model does not treat it as more authoritative than the task.
4. **Explicit file hints**, only when supplied, as a bulleted list labeled "inspect only as needed". Each hint is JSON-quoted on its own line; `validateFileHints()` has already rejected control characters and paths outside the validated `cwd`, so the list cannot carry extra prompt lines.
5. **Role limits** (every role): the role's `degradation` paragraph from `src/roles.ts`, passed by `index.ts` as `roleLimits`. It states the tools the role does not have and the exact fallback to use ("Proposed changes" for a researcher asked to edit, "Decisions needed" with research questions for a worker asked to browse, naming the capable role for a scout), so a misrouted task degrades into a usable partial result instead of a fabricated or aborted one. The bundled plugin agents carry the same rule in their system prompts, so the guidance holds even if a caller bypasses this extension's prompt assembly.
6. **Command policy** (write-capable roles only): the block `buildCommandPolicySection()` builds from the `allowedCommands` list the caller resolved via `loadAllowedCommands()` in `src/agy-settings.ts` — see "Parent-side settings read" in `docs/permissions.md` for where that list comes from and what is deliberately excluded from it. Read-only roles (`scout`, `researcher`) never receive this section because neither has a `run_command` tool.

A section absent from a given call (no context, no files, read-only role) is omitted entirely rather than left as an empty placeholder.

## Denial handling

The runner records tool-level denials as they stream in: a `step_update` with `step_type: "tool"` and `state: "ERROR"` whose `tool_info.error` names a permission failure is captured (tool name, a bounded primary parameter drawn from `tool_info.parameters` such as the command line or path, and the error message) as it arrives. The terminal `result` event's own `denied_actions` array — present on Agy CLI 1.1.26, see `docs/permissions.md` — is folded into the same set of denied-tool records.

- On a `SUCCESS` result with one or more denials, `runAgy()` still resolves, but sets `escalationRequired: true` and opens the diagnostics with an actionable notice naming the denied tool, its bounded argument, and a suggested Agy allow-rule form (`command(<CommandLine>)`, `read_file(C:/...)`, `write_file(C:/...)`, `read_url(<host>)`) — this covers the case where Agy reports success with an empty response after a headless denial.
- On a non-`SUCCESS` terminal status (for example `CANCELED`) with denials, `runAgy()` rejects with `AgyRunnerError` using a dedicated error code rather than the generic status-failure code, and the message opens with an explicit "ESCALATION REQUIRED ... not a user cancel" line so the caller cannot mistake a headless permission denial for someone cancelling the run.

The suggested-rule form is derived only from the denied tool's own bounded arguments; it is advisory text for the owner to review, never an instruction to add a rule automatically, and it never suggests disabling permission checks.

## Auto-retry

`src/retry.ts`'s `runAgyWithDenialRetry()` is the only entry point `index.ts`'s `executeRole()` uses to call `runAgy()`, so it wraps every role-tool call. Sequence:

1. **Attempt 1** runs normally through `runAgy()`.
2. **Decision** (`shouldRetryAfterDenial()`): a retry is worth a second model turn only when the run has a `conversationId`, `escalationRequired` is true, and the response text is empty or whitespace-only. A denied run that still produced substantive text is returned as-is, with no retry. The same test is applied to a thrown `AgyRunnerError` with code `permission_denied` that still carries a `conversationId` — the case where the trajectory ended `CANCELED` rather than `SUCCESS`.
3. **Follow-up turn:** `buildDenialFollowUpTask()` builds a policy notice naming the denied tool call(s) from `deniedTools` (tool name plus a bounded parameter), or — when the stream carried no per-step tool `ERROR` and only the terminal `denied_actions`/stderr evidence exists — the denied permission category via a fixed `ACTION_HINTS` map (e.g. `command` → "run_command (any shell command)"). It forbids repeating the denied call and instructs the model to finish the rest of the task, then list what was skipped under "Decisions needed" together with the allow rule the owner would need.
4. **Attempt 2** resumes the exact same conversation via `runAgy()`'s existing `--conversation <id>` continuation path, with `context`/`files` left unset (they are already in the conversation history). Role, model, and mode are unchanged; no permission is added.
5. **Result:** `MAX_DENIAL_RETRIES = 1` bounds this to a single continuation. The result carries `retry: AgyRetryInfo` (first attempt's status, denied tools/actions, and notice), and `formatModelVisibleResponse()`/`formatRetryNotice()` in `src/runner.ts` prepend a `[Agy auto-retry]` paragraph to the model-visible text — even when the continuation succeeded cleanly — so the owner still sees the original denial and its suggested allow rule. If the continuation itself throws, `runAgyWithDenialRetry()` rethrows with the first attempt's notice prefixed to the error message.

Tool parameter `auto_retry` (default `true`) disables this per call; the composite research_apply tool's worker leg also accepts and forwards it.

## Composite research_apply

`src/research-apply.ts`'s `executeResearchApply()` implements the `agy_research_apply` tool as two role-tool legs behind one Pi UI confirmation:

1. **Gate:** `authorizeResearchApply()` requires `ctx.hasUI`; it is denied headlessly, mirroring `authorizeWriteRole`. The confirmation message (`buildResearchApplyConfirmationMessage()`) states that the researcher leg is web-only/read-only and the worker leg may edit files and run approved commands.
2. **Researcher leg:** the tool calls a `RoleRunner` callback with `role: "researcher"` and `task: buildResearchTask(question)`; `index.ts` supplies its own `executeRole()` as that callback, so this leg goes through the same validation, preflight, and denial-retry path as a standalone `agy_researcher` call. It never receives the caller's `context` or `files` — those parameters exist only on the tool's own schema for the worker leg.
3. **Leg-failure check:** `researchLegFailed()` treats a non-`SUCCESS` status, `escalationRequired`, or an empty response as "no usable brief." When it does, the apply leg is skipped and the tool returns a result naming the research leg's own text, with `details.legs = { research }` and no `apply`.
4. **Apply leg:** the `RoleRunner` is called again with `role: "worker"`, `task: buildApplyTask(applyTask)`, `context: buildApplyContext(brief, userContext)`, the caller's `files`, and `auto_retry`, plus `internal: { skipWriteGate: true }`. `buildApplyContext()` labels the brief "web-derived, untrusted", bounds the combined context to `MAX_APPLY_CONTEXT_CHARS` (30,000 characters), and truncates the brief first so a short explicit parent context survives intact.
5. **Seam:** `index.ts`'s `executeRole()` only honors `internal.skipWriteGate` when `ctx.hasUI` is also true (`if (!(internal.skipWriteGate && ctx.hasUI))`), so the worker leg never prompts a second time and headless calls never become write-capable through this path — the one up-front confirmation is the only gate for both legs.
6. **Errors:** if the apply leg throws after a successful research leg, `executeResearchApply()` rethrows with the research brief preserved (bounded to 8,000 characters) so the research work is not lost.
7. **Output:** on success the result concatenates "## Research (agy_researcher)" and "## Apply (agy_worker)" sections (bounded by `boundPiOutput`) and sets `details.role = "research_apply"` with `details.legs = { research, apply }`.

Reusing `index.ts`'s `executeRole()` as the `RoleRunner` is what lets the composite tool inherit role validation, the command-policy block, preflight, and denial-retry without re-implementing any of them.

## Doctor and preflight

`src/doctor.ts` provides two related, read-only, no-quota checks that mirror the same failure modes documented in "Denial handling" above, but catch them before any quota is spent:

- **`runAgyDoctor()`** (the `agy_doctor` tool and `/agy_doctor` command) runs the full check list: platform/environment support (`assertSupportedAgyPlatform`, win32 required-source-env names), executable resolution (`resolveAgyExecutable`), CLI version against `VERIFIED_AGY_CLI_VERSIONS` (warns on drift, never fails), role-plugin presence against `REQUIRED_AGY_ROLES` by spawning `agy agent`, settings-file readability, cwd read/write coverage (`analyzePermissions`), Windows file-rule form (`isWellFormedWin32FileRule`), configured `command()` allow rules, and sensitive-path deny coverage against a fixed `SENSITIVE_HOME_SUFFIXES` list mirrored from `docs/permissions.md`. It ends with a fixed "Scope caveat" check noting that Agy shared config and project-level grants are not inspected. The only processes it ever spawns are `agy --version` and `agy agent`, through the same `buildAgyChildEnv`-sanitized child environment, `shell: false`, and a bounded (15 s default) timeout as `runAgy()` itself — it never spawns a full delegation. By contract `runAgyDoctor()` never throws: every failure becomes a `fail`-level `DoctorCheck` instead, so a caller can always render a report.
- **`preflightCwdCoverage()`** is the cheap, no-spawn half: it reads only the settings file (same 256 KiB cap as `loadAllowedCommands()`) and reports whether a `read_file(...)`/`write_file(...)` rule covers one `cwd`, touching nothing else.

`index.ts`'s `executeRole()` calls `preflightCwdCoverage()` automatically for every role-tool call except `researcher` and except an explicit conversation continuation (`conversation_id` supplied), and it sits before both the write-gate confirmation (`authorizeWriteRole`) and any process spawn:

- When settings are readable and no `read_file(...)` rule covers `cwd`, the call is refused immediately with a message naming the exact rule to add — no confirmation is shown and nothing is spawned.
- When settings are unreadable/unavailable, or (for a write-capable role) no `write_file(...)` rule covers `cwd`, a `[Agy preflight]` notice line is prefixed to the eventual result instead of blocking the call.
- `skip_preflight` (default `false`) skips this check entirely, for rules the preflight cannot see (Agy shared config, project-level grants).

## Slash commands and skills

Six slash commands (`/agy_scout`, `/agy_worker`, `/agy_delegate`, `/agy_researcher`, `/agy_research_apply`, `/agy_doctor`) are registered next to the tools, all from `src/commands.ts`. The four role commands and `/agy_research_apply` share a `busyOrEmptyGuard` (usage hint when empty, busy notice when `ctx.isIdle()` is false) and then inject a deterministic prompt via `pi.sendUserMessage` — `buildRolePrompt()` for a role, `buildResearchApplyPrompt()` for the composite tool — so the normal agent turn and tool gate apply. `/agy_doctor` only checks `ctx.isIdle()` (it takes no task argument) and sends the fixed `DOCTOR_PROMPT`, which asks the model to show the doctor report verbatim and not start any delegation while a check is `[FAIL]`. Bundled `skills/agy-*/SKILL.md` files (five: `agy-scout`, `agy-worker`, `agy-delegate`, `agy-researcher`, `agy-research-apply`) mirror the tools for natural-language triggering; they only instruct the agent to call the matching tool and do not bypass any gate. `agy_doctor` has no matching skill — it is reached only through its tool or slash command. Command arguments are bounded by `boundCommandArgs` (UTF-8-safe, 8,000 characters, truncation notice).

Each role in `src/roles.ts` carries a `boundary` string stating what that role explicitly cannot do (no web tools for worker/delegate, no local file tools at all for researcher, no web for scout); `index.ts` folds it into the tool description so the parent model sees the boundary before deciding how to route a request. A shared `ROLE_CHAINING_GUIDE` documents the research-then-edit pattern: `agy_researcher` first, then `agy_worker`/`agy_delegate` with the brief passed as `context`, since no single role does both — or, in one call, `agy_research_apply`. The bundled skills mirror this with "Do not use when" lines pointing to the correct role instead.
