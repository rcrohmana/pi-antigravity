# Permissions and threat model

- The extension invokes only the installed official `agy.exe`; it does not call Google APIs or inspect Agy auth files.
- `shell: false` and an argument array prevent task text from becoming a shell command or changing the child cwd.
- `cwd` is canonicalized and must be the current Pi workspace or a descendant; symlink escapes are rejected for working-directory selection. **It is not a filesystem write sandbox.** The effective read/write scope is determined by Agy `read_file(...)` / `write_file(...)` permission rules, which must be configured to the intended workspace roots.
- `worker` and `delegate` require confirmation in interactive Pi UI and are denied without UI. Before process creation, a short confirmation identifies the role, the canonical workspace, a bounded and sanitized task preview (200 characters), up to three file hints, the `command(...)` targets Agy settings allow (or that none are, or that settings were unreadable), and whether a `write_file(...)` rule covers the workspace; it states that it may edit files and run approved commands; it does not render task, workspace, context, or file-hint previews. The runner does **not** pass `--sandbox`; rejection happens before process creation.
- `scout` and `researcher` have no file-write or command tools and run in Agy's flagless default mode (the `--mode` flag is omitted; CLI 1.1.25 accepts only `accept-edits`/`plan`). Scout is local-only; researcher is web-only and has no local-file tools. Explicit context sent to researcher requires a Pi UI confirmation and is denied headlessly.
- Every local agent sets `inheritCustomizations: false`, preventing ambient skills, rules, MCP servers, plugins, and nested-agent behavior from expanding these boundaries.
- No route adds `--dangerously-skip-permissions`. Agy's own scoped permission rules remain authoritative for command, file, and web operations.
- **Command policy prompt block:** for `worker`/`delegate` only, the task prompt sent to Agy includes a "Command policy" section listing the exact `command(<target>)` allow-rule targets found in the owner's Agy settings, so the model is told up front which commands can run instead of probing and hitting a headless denial. This is prompt text the model can in principle ignore or a hostile task/context could try to talk it out of; it is not a security boundary. Agy's own `permissions.allow`/`permissions.deny` rules are the actual enforcement point regardless of what the prompt says. See "Parent-side settings read" and "Denial diagnostics" below.
- **Role-limits prompt block:** every role's task prompt also carries a fixed "Role limits (fixed, not negotiable)" paragraph (`RoleConfig.degradation`), and each bundled plugin agent repeats it as a rule: a researcher asked to touch a file must return the edit under "Proposed changes" and never claim to have read or written a file; a worker/delegate asked for online sources must not invent citations, URLs, or facts and must list the research questions under "Decisions needed"; a scout must name the role that can do what it cannot. This shapes model behaviour so a misrouted task yields a usable partial result instead of a fabricated one; it grants nothing. The frontmatter tool allow-lists (enforced at runtime, see above) and Agy's permission rules are what actually prevent the researcher from writing or the worker from fetching.
- **File hints are paths, not text:** `validateFileHints()` rejects any hint containing a control character (newline, tab, NUL, DEL) and any hint that does not resolve to the validated `cwd` or a descendant of it, before the write gate and before any spawn; the runner then JSON-quotes each hint on its own line. A hint therefore cannot add instructions to the prompt or point Agy outside the workspace. This is prompt hygiene: Agy's `read_file`/`write_file` rules remain the enforcement point for what is actually readable.
- Model-visible output and diagnostics are bounded to 50 KiB UTF-8 and 2,000 lines with an explicit truncation marker. The bridge never reads Agy credential files or serializes hidden Pi context/auth into the prompt. The child receives a fresh minimal allow-listed environment (`PATH` everywhere; Windows process/profile/identity variables and POSIX home/temp/XDG variables, see "Child environment isolation" in `docs/architecture.md`); parent provider keys, generic CI, proxy, custom-CA, Node preload, and Pi variables are not inherited. On Windows, every `runAgy()` call — including calls with injected test spawn implementations — requires the full libuv runtime variable set to exist in the source environment and fails closed before any spawn function runs with names-only diagnostics when it does not, so nothing is filled from ambient `process.env`; the Windows identity variables `LOGONSERVER`, `SYSTEMDRIVE`, `USERDOMAIN`, and `USERNAME` are explicit allow-listed metadata. Agy authentication must use its local documented login/configuration mechanism. Residual risks: allow-listed path/home/temp and identity variables remain identity/capability metadata and can expose path topology or host identity; isolation does not protect on-disk credentials, a malicious `PATH` executable, child-controlled output, or a pre-existing Agy daemon holding an older environment. Command behavior may change because `CI`, locale, time-zone, proxy, custom-CA, and session variables are absent; a startup/authentication failure must be fixed by reviewing a named non-secret runtime dependency, never by restoring wholesale inheritance. No live Agy synthetic-canary acceptance has been recorded for any platform yet; it is owner-approval gated.

The local install helper is opt-in (`-ConfirmInstall`) and is not run by tests.

## Headless permission behavior (verified on CLI 1.1.25)

Empirical findings from live headless probes (evidence preserved in the AGY-003 smoke/activation evidence directories):

- **Headless auto-denies `read_file` and `read_url` without explicit allow rules — including in-workspace reads.** The workspace's `trustedWorkspaces` entry does not apply in headless mode, and the `--sandbox` flag does not change this (verified with identical probes with and without it). Denied calls surface as `TOOL_ERROR: user denied permission for read_file(<path>)` with stderr `jetski: no output produced — a tool required the "read_file" permission that headless mode cannot prompt for, so it was auto-denied`, and the run still reports `SUCCESS` with an empty response. The extension classifies this stderr as `escalationRequired`.
- **The only empirically working Windows file-rule form is `read_file(C:/Users/<you>/...)` — drive letter plus forward slashes.** Drive-less `read_file(Users/<you>/...)` and leading-slash `read_file(/Users/<you>/...)` both fail to match any path (bisected across identical probes).
- **The frontmatter `tools` allow-list IS enforced at runtime.** A scout asked to call `read_url_content` (not in its list) reported the tool unavailable and escalated; a scout instructed to write a file reported `write_to_file` is not available in its toolset and never attempted the write. `init.tools` advertises the full CLI catalog but is NOT the effective toolset — role boundaries hold even though the init payload looks permissive.
- **Command execution matrix (verified on CLI 1.1.25):** headless `run_command` requires a matching `command(<cmd>)` allow rule AND only works WITHOUT the `--sandbox` flag — with `--sandbox`, every `run_command` hits `escalate_admin` auto-denial (`context canceled` TOOL_ERROR). `toolPermission: "proceed-in-sandbox"` has no effect on headless command behavior. File read/write flows work in both modes given `read_file`/`write_file` rules. Per project-owner decision, this extension no longer passes `--sandbox` for any role; command safety relies on scoped `command()` allow rules, the Pi write gate, and the sensitive-folder deny rules.
- **Example Agy settings shape (adapt for any machine)** (in `%USERPROFILE%\.gemini\antigravity-cli\settings.json`, where `<you>` is your Windows username): use `read_url(*)` only when broad academic/web research is required, and keep it paired with the web-only researcher role. For local access, prefer individual roots such as `read_file(C:/Projects/<approved-project>)`; do **not** allow the entire home directory. Keep explicit source fixtures only when needed, such as `read_url(antigravity.google)`, `read_url(github.com)`, and `read_url(google.github.io)`. Recommended `permissions.deny` includes `read_file(C:/Users/<you>/.ssh)`, `read_file(C:/Users/<you>/.gnupg)`, `read_file(C:/Users/<you>/.aws)`, `read_file(C:/Users/<you>/.azure)`, `read_file(C:/Users/<you>/.config/gcloud)`, `read_file(C:/Users/<you>/.gemini)`, `read_file(C:/Users/<you>/.npmrc)`, `read_file(C:/Users/<you>/.git-credentials)`, `read_file(C:/Users/<you>/.kube)`, `read_file(C:/Users/<you>/.docker)`, `read_file(C:/Users/<you>/.env)`, and `read_file(C:/Users/<you>/.pi/agent)`, plus known-working loopback/metadata guards `read_url(localhost)`, `read_url(127.0.0.1)`, `read_url(169.254.169.254)`. Verify any wildcard/range rule for private LAN or nested `.env` files before relying on it. `write_file`/write-tool rules for `worker`/`delegate` remain a separate owner-controlled decision.

### Verified on CLI 1.1.26

A live probe (`echo probe`, run by `worker` with no matching `command()` allow rule) is captured verbatim in `tests/fixtures/denied-command.ndjson` and `tests/fixtures/denied-command.stderr.txt`. Every 1.1.25 finding above still held; two things are new:

- **The denial is now visible mid-stream, not only as an empty final response.** The denied step arrives as a `step_update` with `step_type: "tool"`, `tool_name: "run_command"`, `state: "ERROR"`, and `tool_info: { name: "run_command", parameters: { CommandLine: "echo probe" }, error: { type: "TOOL_ERROR", message: "permission check failed for command \"echo probe\": user denied permission to run command:\necho probe" } }`.
- **The terminal `result` carries a new `denied_actions` array**, e.g. `denied_actions: [{ action: "command", display_name: "RunCommand" }]`, alongside `status: "SUCCESS"` and `response: ""` in this probe. In a separate, longer trajectory the same kind of denial produced a terminal `status: "CANCELED"` instead of `SUCCESS`; both are real outcomes of a headless permission denial, and neither is a user-initiated cancel even though `CANCELED` reads that way.
- **stderr still carries the documented explanatory line**, unchanged in substance from 1.1.25: `jetski: no output produced — a tool required the "command" permission that headless mode cannot prompt for, so it was auto-denied. Add an allow-rule under permissions.allow in settings.json (e.g. command(<target>)).` The stderr message also offers a flag that auto-approves all tools instead; the extension never uses it, regardless of what the message suggests.
- **A `CANCELED` trajectory can end with no per-step tool `ERROR` ever streamed for the denial.** In that case the only evidence is the terminal `result`'s `denied_actions` array and/or the stderr explanatory line above — never a `step_update` naming the specific denied call. `deniedActionsFromDiagnostics()` in `src/runner.ts` covers this: when neither per-step evidence nor `denied_actions` names anything, it derives the denied permission category (e.g. `command`) from the stderr line instead, so the run is still classified as a denial rather than a bare status failure, and the auto-retry follow-up (see "Bounded auto-retry" below) names the permission category rather than a specific call in that case.
- **Headless `--conversation <id>` resume works and streams normally.** Live-verified on CLI 1.1.26: a first attempt `CANCELED` on a denied `echo probe` was continued headlessly with `--conversation <id>` under `--input-format stream-json`/`--output-format stream-json`, and the continuation completed the rest of the task (the resumed conversation reported two turns in total). This is the mechanism the bounded auto-retry relies on (see "Auto-retry" in `docs/architecture.md` and "Bounded auto-retry" below).
- Everything else documented for 1.1.25 — auto-deny of `read_file`/`read_url` without allow rules, the `read_file(C:/Users/<you>/...)` rule form, `command()` rules being required for headless command execution, and `--sandbox` turning every command into an `escalate_admin` denial — was reproduced unchanged on 1.1.26.

### Parent-side settings read

Before spawning `worker` or `delegate`, the parent extension (not Agy, and not the model) reads Agy's own `settings.json` — `%USERPROFILE%\.gemini\antigravity-cli\settings.json` on Windows, `~/.gemini/antigravity-cli/settings.json` on POSIX — and extracts only the string entries under `permissions.allow` shaped `command(<target>)`, capped at 50 entries and 200 characters per target. Nothing else in that file is read into any memory-visible output: not `permissions.deny`, not `trustedWorkspaces`, not any other key the file happens to contain. The file is opened read-only and is never modified.

This is not a credential read. A `command(<target>)` entry names an executable or command the owner already chose to allow; the settings file is Agy's own local permission configuration, not a credential store, and no token, key, or auth material is parsed out of it. The extracted targets are appended to the task prompt as advisory text only (the "Command policy" block described above and in `docs/architecture.md`); they carry no runtime authority themselves. If the file is missing, unreadable, oversized, or not valid JSON, the parent proceeds with an empty command list, and the tool result carries an `[Agy settings notice]` line naming a short non-secret reason (for example `ENOENT`, "invalid JSON", or "too large") — never file content.

### Denial diagnostics

The runner tracks every denied tool step observed in the stream — tool name, a bounded primary parameter such as the command line or file path, and the tool's error message — together with the terminal result's `denied_actions` array, and turns them into an actionable notice instead of a bare status line:

- **`SUCCESS` with denials:** the run still resolves normally, but `escalationRequired: true` is set and the model-visible diagnostics open with the actionable denial notice, even when the response text itself is empty.
- **Non-`SUCCESS` with denials (for example `CANCELED`):** the runner throws `AgyRunnerError` with error code `permission_denied`, whose message opens with "ESCALATION REQUIRED: Agy ended the run with status CANCELED after a headless permission denial (not a user cancel)" so the owner is not misled into treating it as someone pressing cancel.

The notice names the denied tool, the bounded argument that triggered the denial, and a suggested rule to add: `command(<CommandLine>)`, `read_file(C:/...)`, `write_file(C:/...)`, or `read_url(<host>)`, depending on which tool was denied. It never suggests disabling permission checks.

**Residual risk:** a suggested rule is derived from arguments the model itself chose to pass to a denied tool call — it is a starting point for the owner to review, not a vetted grant. Never add a suggested rule blindly, and be especially cautious with broad `command(...)` targets (for example a shell-invoking form like `command(cmd /c ...)`): read and understand exactly what the rule permits before adding it to `permissions.allow`.

## Bounded auto-retry

`runAgyWithDenialRetry()` (`src/retry.ts`) continues the same Agy conversation once after a headless denial that produced no usable output; see "Auto-retry" in `docs/architecture.md` for the exact decision logic and sequence. From a threat-model perspective:

- The continuation resumes the **same conversation** via `--conversation <id>`; it is not a new, differently-scoped run. Role, model, mode, and Agy permission rules are all unchanged, and no permission is added — the retry can only ask the model to finish without the denied call, never grant the call itself.
- The follow-up turn sent into the conversation (`buildDenialFollowUpTask()`) is short, deterministic text naming the denied tool or permission and forbidding a repeat. It sends no new `context` or file hints beyond what the original call already supplied, so the retry cannot be used to smuggle additional untrusted content into the conversation.
- The first attempt's denial notice is deliberately kept in the model-visible output (`[Agy auto-retry]`) even when the continuation completes cleanly, so the owner is never left unaware that a call was denied and what allow rule they might add — a clean-looking final response does not mean nothing was blocked.
- **Residual risk:** the continuation is one additional model turn of quota per denied run; pass `auto_retry: false` to disable it if that cost is unwanted. The model can still choose to attempt a *different* denied tool during the continuation, not the one named in the notice; headless Agy auto-denies that too, and since the retry budget (`MAX_DENIAL_RETRIES = 1`) is already spent, the run simply ends with that second denial rather than retrying again — visible through the normal denial diagnostics above, not a further `[Agy auto-retry]` notice.

## Composite research_apply gate

`agy_research_apply` (`src/research-apply.ts`) runs two role-tool legs — `agy_researcher` then `agy_worker` — behind a single gate rather than two:

- **One confirmation covers both legs.** `authorizeResearchApply()` requires `ctx.hasUI` and one `ctx.ui.confirm()` call before either leg starts, and is denied outright without an interactive UI. The confirmation message names both legs' capabilities (researcher: web-only, read-only; worker: may edit files and use approved commands), so the owner is not agreeing to something narrower than what actually runs.
- **The researcher leg never receives explicit context or file hints.** The tool's `context` and `files` parameters exist only for the worker leg; the researcher's task is built from the research `question` alone. This matters because researcher is web-only — anything handed to it as context is a potential exfiltration vector through a fetched URL's query string (see "Broad web access" below) — so the composite tool structurally prevents that leg from ever seeing caller-supplied context, rather than relying on the model to omit it.
- **`skipWriteGate` only applies with UI.** The worker leg runs with an internal `skipWriteGate` flag so it does not ask for a second confirmation, but `src/execute-role.ts`'s `executeRole()` only honors that flag when `ctx.hasUI` is also true. A headless call cannot reach the worker leg at all, because the up-front gate already denies it, so `skipWriteGate` can never turn a headless call into a write-capable one.
- The worker leg still goes through the same preflight, command-policy block, and denial-retry as a standalone `agy_worker` call; the composite tool changes only how the confirmation and context are assembled, not what the worker is allowed to do.

## Doctor / preflight

`src/doctor.ts` reads only Agy's own `settings.json` (the same file and the same `permissions.allow`/`permissions.deny` entries described above) and, for the full `agy_doctor` report, spawns two read-only Agy CLI probes: `agy --version` and `agy agent` (which lists installed role plugins). Both probes use the same allow-listed, minimal child environment as a real delegation, the same absolute-executable resolution, `shell: false`, and a bounded 15-second timeout; neither probe can edit a file, run a caller-chosen command, or reach the network beyond what those two subcommands themselves do. The cheaper `preflightCwdCoverage()` path used automatically inside every role-tool call spawns nothing at all — it only reads the settings file.

- **Suggested fix rules must be reviewed before adding**, exactly like the denial-diagnostics suggested rules above: a `[FAIL]` check's `fix` line (for example `add read_file(C:/Users/you/project) to permissions.allow`) is derived from the workspace `cwd` the doctor was asked to check, not from anything a model chose, but it is still advisory text for the owner to evaluate, never an instruction to apply automatically.
- **Preflight refusal happens before confirmation and before any spawn.** Inside `executeRole()`, when Agy settings are readable and no `read_file(...)` rule covers the resolved `cwd`, the call throws immediately — before the Pi UI confirmation and before any Agy process is created. This is a fast, no-quota fail-closed check, not a permission escalation: it can only ever refuse a call that headless Agy would have auto-denied anyway.
- **`skip_preflight: true` semantics.** The preflight can only see rules inside the one settings file it reads (`%USERPROFILE%\.gemini\antigravity-cli\settings.json` / `~/.gemini/antigravity-cli/settings.json`); it does not see Agy shared config (`~/.gemini/config/config.json`) or project-level permission grants, so a workspace genuinely covered through one of those sources would otherwise be refused by a preflight blind to it. `skip_preflight: true` is the legitimate escape hatch for exactly that case. It is not a way to bypass Agy's own enforcement: headless Agy still auto-denies any call the rules do not actually cover, so skipping the preflight only removes the extension's own early, advisory check — it never widens what Agy itself allows.

## Broad web access (verified on CLI 1.1.25)

- **`read_url(*)` works as a wildcard allow rule.** A live researcher probe fetched `https://docs.b.ai/llmservice/api/` end to end (correct facts returned, canonical URL cited). Web search itself is the Gemini model's native capability and is not gated by `read_url`; the rule governs only the page-content fetch tool.
- **Deny wins over the wildcard.** A probe asking for `http://localhost/` was rejected with `permission check failed for read_url "localhost": Permission denied for read_url(localhost). Matches user-configured deny rule.` and the model reported the denial honestly.
- **Broad academic research model:** researcher retains broad fetch for papers, publishers, DOI redirects, and repositories, but it is web-only. It cannot read local files, and supplied explicit context is gated in interactive Pi UI and denied headlessly. Use scout for local evidence, then provide researcher only selected non-sensitive findings.
- **Residual risks of broad fetch:** the model can fetch arbitrary URLs, so query strings can exfiltrate supplied task/context to a hostile domain (prompt-injection vector); fetched pages are untrusted content entering the model context; `search_web` is also an outbound search-provider boundary. Private LAN IP ranges (e.g. `192.168.*`) are not enumerated by the deny guards and must be empirically validated before relying on range/wildcard rules; loopback/metadata are denied as above.
