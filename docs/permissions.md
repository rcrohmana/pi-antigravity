# Permissions and threat model

- The extension invokes only the installed official `agy.exe`; it does not call Google APIs or inspect Agy auth files.
- `shell: false` and an argument array prevent task text from becoming a shell command or changing the child cwd.
- `cwd` is canonicalized and must be the current Pi workspace or a descendant; symlink escapes are rejected for working-directory selection. **It is not a filesystem write sandbox.** The effective read/write scope is determined by Agy `read_file(...)` / `write_file(...)` permission rules, which must be configured to the intended workspace roots.
- `worker` and `delegate` require confirmation in interactive Pi UI and are denied without UI. Before process creation, the confirmation shows the role, canonical workspace, bounded previews of task/context, supplied file hints, and the actual capabilities: file creation/replacement subject to Agy write rules and command execution subject to matching `command()` rules. The runner does **not** pass `--sandbox`; rejection happens before process creation.
- `scout` and `researcher` have no file-write or command tools and run in Agy's flagless default mode (the `--mode` flag is omitted; CLI 1.1.25 accepts only `accept-edits`/`plan`). Scout is local-only; researcher is web-only and has no local-file tools. Explicit context sent to researcher requires a Pi UI confirmation and is denied headlessly.
- Every local agent sets `inheritCustomizations: false`, preventing ambient skills, rules, MCP servers, plugins, and nested-agent behavior from expanding these boundaries.
- No route adds `--dangerously-skip-permissions`. Agy's own scoped permission rules remain authoritative for command, file, and web operations.
- Model-visible output and diagnostics are bounded to 50 KiB UTF-8 and 2,000 lines with an explicit truncation marker. The bridge never reads Agy credential files or serializes hidden Pi context/auth into the prompt; the child inherits the parent environment, which remains a trust boundary for external Agy execution.

The local install helper is opt-in (`-ConfirmInstall`) and is not run by tests.

## Headless permission behavior (verified on CLI 1.1.25)

Empirical findings from live headless probes (evidence preserved in the AGY-003 smoke/activation evidence directories):

- **Headless auto-denies `read_file` and `read_url` without explicit allow rules — including in-workspace reads.** The workspace's `trustedWorkspaces` entry does not apply in headless mode, and the `--sandbox` flag does not change this (verified with identical probes with and without it). Denied calls surface as `TOOL_ERROR: user denied permission for read_file(<path>)` with stderr `jetski: no output produced — a tool required the "read_file" permission that headless mode cannot prompt for, so it was auto-denied`, and the run still reports `SUCCESS` with an empty response. The extension classifies this stderr as `escalationRequired`.
- **The only empirically working Windows file-rule form is `read_file(C:/Users/<you>/...)` — drive letter plus forward slashes.** Drive-less `read_file(Users/<you>/...)` and leading-slash `read_file(/Users/<you>/...)` both fail to match any path (bisected across identical probes).
- **The frontmatter `tools` allow-list IS enforced at runtime.** A scout asked to call `read_url_content` (not in its list) reported the tool unavailable and escalated; a scout instructed to write a file reported `write_to_file` is not available in its toolset and never attempted the write. `init.tools` advertises the full CLI catalog but is NOT the effective toolset — role boundaries hold even though the init payload looks permissive.
- **Command execution matrix (verified on CLI 1.1.25):** headless `run_command` requires a matching `command(<cmd>)` allow rule AND only works WITHOUT the `--sandbox` flag — with `--sandbox`, every `run_command` hits `escalate_admin` auto-denial (`context canceled` TOOL_ERROR). `toolPermission: "proceed-in-sandbox"` has no effect on headless command behavior. File read/write flows work in both modes given `read_file`/`write_file` rules. Per project-owner decision, this extension no longer passes `--sandbox` for any role; command safety relies on scoped `command()` allow rules, the Pi write gate, and the sensitive-folder deny rules.
- **Example Agy settings shape (adapt for any machine)** (in `%USERPROFILE%\.gemini\antigravity-cli\settings.json`, where `<you>` is your Windows username): use `read_url(*)` only when broad academic/web research is required, and keep it paired with the web-only researcher role. For local access, prefer individual roots such as `read_file(C:/Projects/<approved-project>)`; do **not** allow the entire home directory. Keep explicit source fixtures only when needed, such as `read_url(antigravity.google)`, `read_url(github.com)`, and `read_url(google.github.io)`. Recommended `permissions.deny` includes `read_file(C:/Users/<you>/.ssh)`, `read_file(C:/Users/<you>/.gnupg)`, `read_file(C:/Users/<you>/.aws)`, `read_file(C:/Users/<you>/.azure)`, `read_file(C:/Users/<you>/.config/gcloud)`, `read_file(C:/Users/<you>/.gemini)`, `read_file(C:/Users/<you>/.npmrc)`, `read_file(C:/Users/<you>/.git-credentials)`, `read_file(C:/Users/<you>/.kube)`, `read_file(C:/Users/<you>/.docker)`, `read_file(C:/Users/<you>/.env)`, and `read_file(C:/Users/<you>/.pi/agent)`, plus known-working loopback/metadata guards `read_url(localhost)`, `read_url(127.0.0.1)`, `read_url(169.254.169.254)`. Verify any wildcard/range rule for private LAN or nested `.env` files before relying on it. `write_file`/write-tool rules for `worker`/`delegate` remain a separate owner-controlled decision.

## Broad web access (verified on CLI 1.1.25)

- **`read_url(*)` works as a wildcard allow rule.** A live researcher probe fetched `https://docs.b.ai/llmservice/api/` end to end (correct facts returned, canonical URL cited). Web search itself is the Gemini model's native capability and is not gated by `read_url`; the rule governs only the page-content fetch tool.
- **Deny wins over the wildcard.** A probe asking for `http://localhost/` was rejected with `permission check failed for read_url "localhost": Permission denied for read_url(localhost). Matches user-configured deny rule.` and the model reported the denial honestly.
- **Broad academic research model:** researcher retains broad fetch for papers, publishers, DOI redirects, and repositories, but it is web-only. It cannot read local files, and supplied explicit context is gated in interactive Pi UI and denied headlessly. Use scout for local evidence, then provide researcher only selected non-sensitive findings.
- **Residual risks of broad fetch:** the model can fetch arbitrary URLs, so query strings can exfiltrate supplied task/context to a hostile domain (prompt-injection vector); fetched pages are untrusted content entering the model context; `search_web` is also an outbound search-provider boundary. Private LAN IP ranges (e.g. `192.168.*`) are not enumerated by the deny guards and must be empirically validated before relying on range/wildcard rules; loopback/metadata are denied as above.
